# ReactiTwin Reproducibility and Configuration Guide

This guide describes the procedure required to reproduce the **ReactiTwin Moving Target Defence (MTD) approach**, including the deployment of the containerised Digital Twin (DT) infrastructures, the network traffic capture and processing, Backdoor-Based Command and Control (BBC2) detection, and reactive DT container rotation.

## 1. Deployment Platform and System Requirements

**Operating system requirement:** ReactiTwin must be deployed on a **GNU/Linux-based operating system**. This requirement results from the use of Kubernetes through MicroK8s in the experimental deployment.

The following software components are required:

* Zeek for network traffic monitoring and connection-level event generation;
* MicroK8s for container orchestration;
* RabbitMQ for message brokering between the network monitoring and detection components;
* Python 3.10 for executing the machine-learning and ReactiTwin components.

## 2. Prerequisite Files

The following files must be available before deploying ReactiTwin. The first four files are generated by executing `RelNet_Model_Building.py`:

    `support.npy`, NumPy array containing the observations constituting the support set used for deployment of the Relation Network model.
    `support_labels.npy`, NumPy array containing the labels associated with the observations in the support set, with a one-to-one correspondence between each observation and its corresponding label. 
    `embedder.h5`, HDF5 file containing the trained observation encoder used in the few-shot learning configuration. 
    `relation.h5`, HDF5 file containing the trained relation model used in the few-shot learning configuration. 
    `onehot_column_name.pkl`, Pickle file containing the fitted One-Hot encoder for the `column_name` categorical feature.

The complete set of model and preprocessing artefacts required by the deployed implementation must be available in the execution environment before starting ReactiTwin.

## 3. Installation of Required Software

### 3.1 Zeek

Download and install Zeek according to the official documentation:

* Download: [Zeek download page](https://zeek.org/get-zeek/)
* Installation guide: [Zeek installation documentation](https://docs.zeek.org/en/current/install.html)

After installation, ensure that the Zeek executable is accessible from the deployment environment and note its binary path

### 3.2 MicroK8s

Install MicroK8s using the official documentation:

[MicroK8s installation and documentation](https://canonical.com/microk8s)

MicroK8s is used as the Kubernetes distribution for deploying and managing the containerised DT infrastructures.

### 3.3 RabbitMQ

Install RabbitMQ using the official installation documentation:

[RabbitMQ installation documentation](https://www.rabbitmq.com/docs/install-debian)

RabbitMQ provides the message-broker infrastructure used to transmit the network-flow information processed by the ReactiTwin detection pipeline.

### 3.4 Python Environment

Install **Python 3.10** and create a dedicated Python virtual environment:

```bash
python3.10 -m venv myvenv
source myvenv/bin/activate
```

Install the Python dependencies required to execute the few-shot learning model:

```bash
pip install numpy==1.26.4 pandas==2.2.2 scikit-learn==1.4.2 tensorflow==2.15.0 matplotlib==3.7.2 seaborn==0.13.2
```

## 4. Deployment of the Containerised Digital Twin Infrastructures

Start the MicroK8s container orchestrator:

```bash
sudo microk8s start
```

Deploy **10 identical containerised DT infrastructures** using the `ReactiTwin_deployment.yaml` deployment manifest:

```bash
sudo microk8s kubectl apply -f ReactiTwin_deployment.yaml
```

The deployed DT prototype corresponds to the data-driven DT implementation described by Rakotonirina et al.:

> Rakotonirina, Harimanga-Yannick, et al. "Addressing data confidentiality and interconnectivity in digital twins: A case study on the hot water cycle of a heat pump test bench." *Array* (2026): 101175.
DOI: https://doi.org/10.1016/j.array.2026.101175

### 4.1 Active and Standby DT Infrastructures

Within the ReactiTwin MTD mechanism, **only one of the ten deployed DT infrastructures is exposed to the Internet at a given time**. The remaining infrastructures are maintained in a passive state (i.e ready but not exposed to internet) and are not directly accessible to end users.

When a BBC2 connection is detected, the ReactiTwin mechanism triggers the reactive rotation of the exposed DT infrastructure.

After deployment, verify the status of the Kubernetes pods:

```bash
sudo microk8s kubectl get pods -A
```

The expected DT infrastructures should be successfully deployed before proceeding with the ReactiTwin execution.

## 5. Preparation of the ReactiTwin Runtime Environment

Activate the Python virtual environment:

```bash
source myvenv/bin/activate
```

Place the following ReactiTwin scripts blelow (strored in this github repositories) in the `myvenv` execution directory:

* `zeek_to_rabbitmq.py`
* `BBC2_countermeasure.py`

For example:

```bash
(myvenv) cp /path/to/zeek_to_rabbitmq.py ./
(myvenv) cp /path/to/BBC2_countermeasure.py ./
```

The required model (from the training process of the Relation Network model) and preprocessing artefacts must also be placed in the same execution environment:

```bash
(myvenv) cp /path/to/support.npy ./
(myvenv) cp /path/to/support_labels.npy ./
(myvenv) cp /path/to/embedder.h5 ./
(myvenv) cp /path/to/relation.h5 ./
(myvenv) cp /path/to/onehot_weird_name.pkl ./
(myvenv) cp /path/to/onehot_weird_notice.pkl ./
(myvenv) cp /path/to/onehot_weird_addl.pkl ./
(myvenv) cp /path/to/onehot_ssl_resumed.pkl ./
(myvenv) cp /path/to/onehot_ssl_established.pkl ./
```

Update **line 29** of the relevant ReactiTwin Python script to specify the path to the directory containing the prerequisite model and preprocessing files.

The specified path must correspond to the actual storage location of these files on the deployment platform.

## 6. Start Real-Time Network Monitoring and RabbitMQ Communication

The `zeek_to_rabbitmq.py` script is responsible for **starting the required RabbitMQ service and the Zeek-based real-time network traffic monitoring pipeline**, as well as forwarding the relevant Zeek connection information to the RabbitMQ message broker.

Before executing the script, ensure that the RabbitMQ service is available on the deployment platform after its installation.

If required, clear the RabbitMQ queue before starting a new experimental run to prevent residual messages from a previous ReactiTwin execution:

```bash
sudo rabbitmqctl purge_queue zeek_conn_queue
```

The `zeek_to_rabbitmq.py` script must then be configured according to the local Zeek installation. In particular, adapt the path to the Zeek executable specified through the `zeek_cmd` dictionary in the script.

Start the real-time network monitoring and RabbitMQ communication pipeline with:

```bash
python zeek_to_rabbitmq.py
```

This script maintains the processing pipeline required by ReactiTwin while the experiment is running.

## 7. Start BBC2 Detection and Reactive Rotation

Open a second terminal and activate the same Python virtual environment:

```bash
source myvenv/bin/activate
```

Start the BBC2 detection and reactive countermeasure component:

```bash
python BBC2_countermeasure.py
```

This component performs BBC2 detection using the trained **Relation Network model**. When a BBC2 connection is detected, ReactiTwin triggers the reactive rotation of the container hosting the currently exposed DT infrastructure.

The reactive rotation changes the DT infrastructure exposed to the Internet, thereby removing the previously exposed (corrupted) container from the active position and replacing it with another safe DT infrastructure container available.

## 8. Stopping the ReactiTwin Processes

To stop either Python process, interrupt the corresponding process from its terminal using:

```text
Ctrl+C
```

Both `zeek_to_rabbitmq.py` and `BBC2_countermeasure.py` should be stopped after completion of the experimental run.

## 9. Collection of Experimental Measurements

### 9.1 Time-to-Detection and Time-to-Remediation

ReactiTwin automatically records the timestamps required to calculate the following experimental metrics:

* **Time-to-Detection (TTD):** denotes the time interval between the arrival of a network flow at the internet-facing network interface of the container orchestrator, and its classification as a BBC2 connection by the relation network model;
* **Time-to-Remediation (TTR):** quantifies the delay between the detection of a BBC2 connection and the complete termination of the pod exposing the DT application to the Internet, thereby providing a direct operational metric of the incident response within ReactiTwin.

The relevant timestamps are automatically recorded by the implementation in `BBC2_countermeasure.py`. Unix timestamps are used to determine the temporal differences between the relevant events.

No additional manual timestamp recording is therefore required during the experimental runs.

### 9.2 Experimental Measurement Campaigns

Measurement campaigns are conducted under the different experimental configurations considered for ReactiTwin. These campaigns generate the empirical TTD and TTR observations used for the subsequent statistical analysis.

The resulting observations can be used to construct **Kaplan–Meier survival curves** and to perform **log-rank tests** when comparing the corresponding experimental configurations.

The TTD and TTR measurements should therefore be retained for subsequent statistical processing and reporting of the experimental results.

To compute the CI 95 of WILSON, Kaplan–Meier survival curves generation and log-rank tests, install this library :
```bash 
pip install statsmodels
 ``` then execute the python script *Log_Rank_Test_for_TTD_TTR.py* in the TTD_TTR_measurement_series in this repository.

## 10. Monitoring Container State Transitions and Dynamic DT Container Rotation

This experiment uses **Prometheus** and **Grafana**, deployed on the server hosting **MicroK8s**, to monitor and document the state transitions of the container hosting the Digital Twin (DT) and the dynamic rotation of DT containers within the **Moving Target Defence (MTD)** approach implemented by ReactiTwin.

### 10.1. Prometheus and Grafana Installation and Configuration

**Prometheus installation and configuration on a GNU/Linux Server:**  
https://prometheus-operator.dev/docs/getting-started/installation/

**Grafana installation and configuration on a GNU/Linux Server:**  
https://grafana.com/docs/grafana/latest/setup-grafana/installation/helm/

### 10.2. Prometheus Measurements

Prometheus is used to execute the following **PromQL** queries.

To monitor the state transitions of the container hosting the DT:

```promql
clamp_max(
  kube_pod_status_phase{namespace="default", pod=~"dt-.*", phase="Running"},
  1
)
```

To monitor the dynamic rotation of the DT container replicas forming the ReactiTwin infrastructure:

```promql
kube_pod_status_phase{namespace="default", pod=~"dt-.*", phase="Running"} == 1
```

These queries provide the monitoring data required to verify the container state transitions and the dynamic rotation of DT container replicas during the experiment.

## 11. Measurement of DT Application Availability During BBC2 Remediation

This experiment measures the availability of remote end-user access to the DT's main application interface during the remediation of a BBC2 connection through ReactiTwin.

### 11.1. Experimental Configuration

All measurements must be performed within the **controlled experimental environment** used to evaluate ReactiTwin and must not be conducted on operational or production systems.

Before each experimental run, ReactiTwin is activated. A virtual PC then requests the container hosting the BBC2, thereby exposing the infected container within the controlled experimental environment and triggering the ReactiTwin remediation process.

The measurements are subsequently collected from a **separate physical PC** connected to the experimental environment, using the DT's main application page URL.

### 11.2. Execution of the Availability Measurement Script

From the physical PC, execute the `availability_measurement.js` script provided in this GitHub repository.

On Windows, the script can be executed from **PowerShell**. On Linux, it can be executed from a **Linux terminal**. The latest stable version of **Node.js** must be installed before running the script.

```bash
node availability_measurement.js
```

The script measures the following performance indicators for the DT's main application page URL during the ReactiTwin attack-remediation phase:

- **Availability**
- **Request error rate**
- **HTTPS end-to-end request latency**

### 11.3. Metric Definitions

**Availability** and **request error rate** are computed as the proportions of HTTPS responses returning successful status codes (**2XX and 3XX**) and failed or unanswered requests, respectively, relative to the total number of requests issued during each observation period.

The **end-to-end request latency** is characterised using the **95th percentile (P95)** of the HTTPS request durations collected during each six-minute observation interval. The P95 therefore represents the latency threshold below which 95% of the observed request durations fall.

### 11.4. Repeated Measurements

The measurements are collected over **six successive executions** of the aforementioned experimental configuration, with each execution covering a **10-minute observation period**.

The resulting measurements are stored in the following CSV file provided in this GitHub repository:

`availability_measurements.csv`

The resulting dataset is used to generate the box plot entitled **“DT Performance Degradation During the Intrusion Remediation Phase in ReactiTwin”**, presented in the submitted paper.

The CSV file provided in this repository therefore contains the measurements required to reproduce the corresponding box plot and to verify the reported *availability*, *request error rate*, and *HTTPS end-to-end request latency* measurements.
